You are a QA engineer doing the second round of a dry run of a local web app and its simulation engine. Round 1 found 13 faults and they have since been fixed. This round has three jobs: prove the fixes hold at their edges, cover what round 1 did not finish, and look for the same kinds of fault in places round 1 did not look. You report; you do not fix. The project is `pm-sim`, in the folder you were started in (Node 24 or newer, TypeScript run directly with type stripping, no build step).

Round 1's work is in `out/dry-run/` (REPORT.md, findings.json, scripts, and a local copy of `playwright-core` under `out/dry-run/node_modules`). Treat that folder as read-only evidence. Read REPORT.md first.

## Ground rules

1. Do not edit anything outside `out/`. Put everything for this round in `out/dry-run-2/` (git-ignored); copy any round 1 script you reuse instead of running it in place, because several write their result files into `out/dry-run/`.    - bash: `PORT=4311 USERS_FILE=out/dry-run-2/users.json node src/server.ts`

   Harnesses that start the app in-process with `createApp({usersFile})` on port 0 are fine and often better. Stop every process you start.

5. Report defects and contradictions only. No style opinions, no refactoring advice. Do not invent findings to fill space.
6. Budget about 75 minutes. Work in the phase order below, and say what you cut if you run short.

## Harness lessons from round 1 (avoid repeating them)

- The third-quarter event name is in the completed quarter's `report.event.name`; the view before the quarter shows only the signal.
- The canonical "do nothing" player sends an explicit idle decision (empty roadmap, reserves 0.05, pace steady, research 0.5, instrument 0.5), not zero allocations.

- Wait for a visible completion element before judging a browser screen; a loading snapshot is not a finding.

## What changed since round 1 (verify each; a wrong statement here is itself a finding)

- Run numbers (`ref`) are random integers from 1 to 2^48 (up to 15 digits), no longer counted from the clock. The route is `/api/runs/(\d+)`.
- Login: each try on a real account is counted before the slow password hash runs; the fifth counted try sets a 60 second lock; a right password clears the count; after a lock runs out the count starts again from zero. Unknown names are never counted.
- Registration: if the accounts file cannot be written, the request fails with 500 and the account does not exist afterwards.
- Request bodies: 65,536 bytes are accepted, 65,537 get a 413 response and the connection is not reset. A POST passes only if the media type before any `;`, trimmed and case-insensitive, is exactly `application/json`; otherwise 415.
- Retention `drop` ids are checked with an own-property test. Venture `commit` ids must be items of the case ("the promises names ..."). Venture range errors use the case's own words for the design and analyst splits.
- Timer: starts when a run screen is first shown, stored in localStorage `pm.timer.<ref>` as `{startedAt, pausedAt, pausedTotal}`; seconds left = minutes*60 minus (pausedAt or now, minus startedAt, minus pausedTotal)/1000; paused by `visibilitychange` (hidden) and `pagehide`, resumed when visible; below zero it shows a leading minus and the `over` style.
- Dialogs (`web/lib.js` `dialog()`): a document-level keydown listener closes on Escape and keeps Tab and Shift+Tab inside the box (buttons, links, inputs, selects, textareas that are not disabled); focus returns to the opener on close; a click on the scrim closes. Callers: `web/play.js` (two) and `web/venture.js` (two).
- The legal page and README now say accounts are read once at startup, so deleting one means stopping the server, editing `data/users.json`, and starting it again.
- `proto/venture/equiv.ts` compares only the two cases that have a prototype. The suite has 111 tests.
